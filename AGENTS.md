# AGENTS.md — atari-juego

Atari 8-bit game in 6502 assembly (MADS assembler): a recreation of the Kaiju / "SUPPA ROBOTTO" game (original rules reverse-engineered from its cc65 binary) with our own code. `README.md` is the player-facing overview (Spanish); no Makefile, CI, tests, or lint. Spanish labels/comments.

## Build & run

- Build: `mads main.asm -o:juego.xex` (MADS 2.1.7)
- Debug build: `mads main.asm -d:DEBUG=1 -o:juego-debug.xex` (not committed, in `.gitignore`). `DEBUG` (default 0 via `.ifndef` in `main.asm`) replaces the title's text line with `txt_debug` ("START LEVEL n"): joystick left/right ±1 level (wrapping 0..NUM_NIVELES-1), sets `etapa_ini`, which `nueva_partida` copies into `etapa` (always 0 in the normal build). Code under `.if DEBUG` in `etapas.asm` (`dbg_selector`/`dbg_texto`), `nivel.asm` and `datos.asm`.
- Run: open `juego.xex` in Altirra (`altirra juego.xex`); control with joystick 1 + trigger
- No test suite — verification is: assemble clean + smoke-test in emulator
- `juego.xex` is a build artifact, not versioned (`.gitignore`): rebuild it after any `.asm` change
- Some `.asm` files may be read-only on disk (check `ls -l`; `chmod u+w <file>` before editing)

## Architecture

- `main.asm` is the only entrypoint (`org $2000`, `run start`). It pulls in everything via `icl`; there is no linker step. Include order: `hardware.asm`, code (`jugador`, `bala`, `sonido`, `hud`, `nivel`, `enemigos`, `balaenemiga`, `celulas`, `partes`, `etapas`), `datos.asm`, `kaiju_graficos.asm`, `MAPAS = *` (+ guard that `MAPAS + MAXPARTES*920` fits before $6000), an `.if * > $6000` guard, `kaiju_titulo.asm` (it does `org $6000` / `org $7000`), an `.if * > PMG` guard, then `org ZONA_NIVELES` + `niveles.asm` (+ `NUM_NIVELES` 1-99 check and an `.if * > ZONA_NIVELES_FIN` guard). Before all of that, an INI segment (`apagar_basic`, assembled at `org PMG` since the game clears that area later) runs as soon as it loads: sets PORTB bit 1 (BASIC ROM off on XL/XE), `BASICF = 1`, `RAMTOP = $C0`, and closes/reopens E: so the OS screen moves to $BC20-$BFFF. Order of XEX segments matters: it must stay first. Note: reopening E: resets the OS color registers (irrelevant, the game sets its own later). Altirra's own XEX loader already disables BASIC, so it can't reproduce the BASIC-on case.
- Memory map: program + data $2000–<$6000 (code only, currently ends ~$375F; then `MAPAS`, MAXPARTES×920 bytes of RAM for the decompressed level parts, not in the .xex, up to ~$45BF: ~6.5 KB free for features; the guards fail the build past $6000), title picture $6000–$6FEF + $7000–$7EAF, `PMG = $8000` (2 KB single-line), `FUENTE = $8800` (1 KB), `PANTALLA = $8C00` (24×40), `DLIST = $8FC0`, `DLIST_T = $9000` (title display list, built at runtime, 209 bytes), `ZONA_NIVELES = $9100`–`ZONA_NIVELES_FIN = $BC00` (levels only, 11008 bytes = `PRESUPUESTO` in the editor; RAM because `apagar_basic` turns BASIC off; the OS screen lives at $BC20+ and is never used by the game). All in `hardware.asm`.
- Game flow (`main.asm` + `etapas.asm`): `titulo` (wait for a fresh button press) → `nueva_partida` (etapa 0, energia 5, puntos 0) → for each stage: `pantalla_level` ("LEVEL n", n = etapa+1, 1-2 digits via `decimal`, 2 s) → `cargar_etapa` → frame loop. Loop exits: `celrest = 0` → `etapa++` (after `NUM_NIVELES`: "YOU ARE SUPER PLAYER" → title); `fin = 1` (a cell was shot) → `energia--`, "TRY AGAIN", same stage again; `energia = 0` → "GAME OVER" → title. Energy and score carry over between stages.
- Level `e` (0..NUM_NIVELES-1, max 99) = `niveles[e]` in `niveles.asm`, generated by the editor (the original Kaiju levels were removed). Format: `.byte parteIni,px,py` (player start), `.byte ancho,alto` (grid of parts, ancho×alto ≤ `MAXPARTES` = 4), then each part row by row as a 23×40 map RLE-compressed (`$FF,n,v` = n×v, any other byte literal; the editor encodes per row, runs ≥4), `.byte nrob,ncel` (whole level), 12-byte robots (parte, x, y, dirA, dirB, pasos, clase, vida, zx0, zx1, zy0, zy1), cells (parte, x, y). `dibujar_nivel` (nivel.asm) decodes every part into its `MAPAS` buffer (`mapas_lo/hi`) via `leer_nivel` and leaves `ptr` after them; `cargar_robots` (enemigos.asm) keeps reading from there (it doesn't draw), so `cargar_etapa` must call them back to back, then `mostrar_parte`.
- Parts (`partes.asm`): `parte` (= `pfil*pancho + pcol`) is the one on screen. `mover_jugador` sets `salida` (`SAL_IZQ/DER/ARR/ABA`) when the player pushes past the x 50–200 / y 40–198 clamp (only possible through a gap in the border); `ver_salida` (frame loop, right after `mover_jugador`) checks there is a part on that side, `guardar_parte` (erases the part's live robots and cells, copies screen rows 1-23 to its `MAPAS`), updates pcol/pfil/parte, puts the player on the opposite edge (px 200/50, py 198/40), `limpiar_pmg` (kills bullets) and `mostrar_parte` (copies `MAPAS` to the screen, draws its cells and robots). So broken blocks, collected cells and dead robots persist. Robots and cells of other parts are frozen: every loop over robots/cells (actualizar_enemigos, contactos, golpear_enemigo, pintar_celulas) skips `rob_parte`/`cel_parte` ≠ `parte`. `MAXROB` = 16 and `MAXCEL` = 18 for the whole level. Robots can't leave the screen through a gap: `libre_robot` (cols 0-38, rows 1-22, 4 free cells) is used by `ae_mover` and `libre_dir`. Changing the format means changing both the asm loaders and `exportarNiveles`/`leerNiveles` in the editor.
- Frame loop: `esperar_paso` (waits `FRAMES_PASO` = 2 frames and bumps `npaso`; `ver_salida` runs right after `mover_jugador`; the cc65 original only managed ~1 loop per 2 frames, so every rule below counts loop steps, not frames) `-> mover_jugador -> animar_jugador -> dibujar_jugador -> actualizar_bala -> actualizar_enemigos -> actualizar_balas_enemigas -> dibujar_celulas -> contactos -> actualizar_sonido -> actualizar_hud`, then the exit checks.
- `hardware.asm` — all equates (shadow registers, GTIA/ANTIC, POKEY, ROM font, zero-page `ptr = $CB` / `ptr2 = $CD`, memory map). Add new hardware addresses here, not inline.
- `datos.asm` — all shared mutable state plus constant tables: player (`px/py`, `ddx/ddy`, `tick/paso/pose/espejo/andando`), bullet, stage state (`etapa`, `energia`, `invul`, `fin`, `cuenta`, `cnt11`), robot arrays `rob_*` (MAXROB 10), cell arrays `cel_*` (MAXCEL 18), `dir_dx/dir_dy`, `persigue`, sound tables `snd_*` (`SND_*`), `POSE_*`/`poses_lo/hi`, `filas_lo/hi`, `dl_datos`, `revtab`. New globals go here. `vida_icono` is no longer drawn; kept for the editor.
- Screen: all 24 rows ANTIC 4 multicolor (no DLI), Kaiju font (`CHBAS = >FUENTE`), colors `KAIJU_COLOR0-2`; row 0 is the HUD. `modo_juego` / `modo_texto(A = font page)` / `modo_titulo` (`nivel.asm`) switch display list, font and colors; `poner_dl` writes `SDLSTL/H` right after a frame so the VBI never copies half an address. Messages use the ROM font (`CHBAS = $E0`) in ANTIC 4 like the original; "LEVEL m-n" uses the Kaiju font (letters $28-$2A, '-' $2B, digits $0A+n). Row r = lines 32+8r..39+8r, column c = HPOS 48+4c..51+4c.
- Title: `kaiju_titulo1` (lines 0-101) and `kaiju_titulo2` (102-195) in separate 4 KB blocks because a 40-byte ANTIC E line cannot cross a 4 KB boundary; `DLIST_T` has a second LMS, then one ANTIC 7 line with `kaiju_txt_titulo`.
- HUD (`hud.asm`, Kaiju layout): cols 0-9 energy icons ($06,$07 per point), cols 10-27 one $34 per remaining cell, cols 29-38 ten digits ($0A+d; first 4 always 0, last 6 from `puntos` BCD). Redrawn only when `hud_dirty`. `sumar_bcd` adds a single BCD digit (A) to `puntos+X` without `SED` (+1: X=2 A=$01; +10: X=2 A=$10; +100: X=1 A=$01).

## Game rules (from the original, verified in an emulator)

- Player: the Kaiju robot (6 poses from `kaiju_graficos.asm`, 8×24 single-line, P0 body `KAIJU_PCOLR0` + P1 outline `KAIJU_PCOLR1`, `GPRIOR = $31` OR-mixing). `dibujar_jugador` reads the pose via `ptr` and assumes each `_p1` sits right after its `_p0`; `datos.asm` checks it with `.if/.error`. Animation: idle → `QUIETO_IZQ`/`QUIETO_DER` by `ddx`; walking alternates A/B every 5 frames; straight up uses `ARRIBA`, otherwise `CAMINA` mirrored via `revtab` when `ddx<0`.
- Movement: 1 px horizontally / 2 lines vertically per frame, diagonal throttled (skip 1 of 4 steps via `npaso & 3`, returning before any move; keep this). X then Y applied separately and undone if `choca` (slides along walls). Player box = 8 columns × pose lines 2-21 (`caja_jugador` → `col0..col1`, `fil0..fil1`). `andando` drives the animation, so pushing a wall shows the idle pose.
- Tiles: `solido` (nivel.asm, used by `choca` and enemy bullets) treats 1-$13, $34-$3F and $58+ as solid; cells ($14-$1B) and enemies ($1C-$33 and shooters $40-$57, also inverse) are passable so `contactos` can handle touching them. Being blocked by the green border (tiles 2/3) calls `herir` (`borde_hiere`).
- Cells (`celulas.asm`): 2×2 chars, animated $18-$1B / $14-$17, swapping at `cuenta` 0 and 6 (12-frame cycle). Touching one collects it (+100). Shooting one sets `fin` (level lost, see flow).
- Enemies (`enemigos.asm`): 2×2 chars at `rob_x/rob_y`, chars `rob_clase` ($9C inverse = COLOR3, or $1C) + 0/4 when facing left (dir 0-3) or + $10/$14 (dir 4-8), alternating with `rob_fase`. Updated every 11 frames; they move one cell every 2 updates (when `rob_fase` returns to 0) and only into 4 empty cells. Directions (measured in the original): 0 up-left, 1 up, 2 left, 3 down-left, 4 down-right, 5 down, 6 right, 7 up-right, 8 stop, 9 = destroyed. Patrol: `rob_dira` while `rob_paso < rob_pasos/2`, else `rob_dirb`; `rob_paso` wraps at `rob_pasos` (0 = keep current dir). If the player's center cell (`pcx/pcy`) is inside the watch zone (cols `rob_zx0..zx1`, rows `rob_zy0..zy1`) the robot switches to `rob_estado = 2` for good and chases with `persigue` (8-way toward the player). HP (`rob_vida`) comes from the level data. Killing one gives +10. Touching one costs 1 energy.
- Shooters (`balaenemiga.asm`): robots with `rob_clase` = `TIROCLASE` ($40, or $C0 inverse = COLOR3); chars `fuente_tirador` (datos.asm, 16 chars copied to FUENTE at $40-$47 / $50-$57 by `iniciar_pantalla`, same +4/+$10 layout as the other robots; the editor has a copy, `FUENTE_T`). They patrol like normal robots and always face the player (`dibujar_robot` compares `rob_x` with `pcx`). When alerted (`rob_estado = 2`) `cazar` keeps distance instead of chasing: `distancia` (Chebyshev, cells from `rob_x/rob_y` to `pcx/pcy`) > `DIST_MAX` (14) → approach, < `DIST_MIN` (6) → flee trying the 5 dirs of `huida` (opposite, its neighbours, the two sideways) with `libre_dir` (after erasing itself), cornered or in range → dir 8 (stand still). From `actualizar_enemigos` (`tirador`, after drawing): every `TIRO_ESPERA` (4) updates (`rob_tiro`, first shot staggered 3+index) they fire (`apuntar`: 16 directions toward the player center from the real pixel deltas, |dx|/2 vs |dy|/4, small*5 < big → straight, small*3 < big*2 → 22.5°, else 45°; speeds `ap_vx/ap_vy`, 4 HPOS / 8 lines like the player bullet) if `distancia` <= `DIST_MAX` and (>= `DIST_MIN` or standing still); otherwise `rob_tiro = 1` to retry on the next update. Alerted shooters move one cell every update instead of every 2 (`veloz` in `ae_mover`); patrol speed is unchanged so the editor preview stays right. `MAXEB` = 2 enemy bullets (`eb_*`): bullet 0 = P2 (`PMG+$600`), 1 = P3 (`+$700`), 4×4 `eb_icono`, color PCOLR2/3 ($44). `actualizar_balas_enemigas` each step: dies outside x 48-203 / y 40-211 or when its center (`bloque_en`) is `solido`; passes over cells and robots; touching the player box → `herir` and dies. No free slot = the shot is skipped. `SND_TIRO`.
- Damage (`herir`): -1 energy unless `invul > 0`; then 50 frames of invulnerability.
- Bullet (missiles 0+1, one at a time, edge-triggered fire, `bdx = ddx`, `bdy = ddy*2`, diagonals ±3/±6, spawn `px+2, py+8`): checks its 4 corners (4×8 box, `bala_px/bala_py`, `bloque_en` → `bcol/bfil`, `ptr2/Y`): every blue block (5) touched breaks (+1) and the bullet dies; the first non-blue thing found decides: cell → `fin = 1`; enemy char → `golpear_enemigo`; border/brick → just dies. `HPOSM1 = bx`, `HPOSM0 = bx+2` (never the same X). COLOR3 ($26) is shared by the bullet and the inverse-char enemies.
- Differences from the original, on purpose: the chase uses a clean 8-way table (the original's chase compared the wrong axis in some cases); our player moves 2 lines vertically per frame (original 1); sounds are simplified (`SND_DISPARO/RECOGER/GOLPE/TIRO`, channel 1); shooters are new (not in the original); the original also charged energy when touching the top screen edge, which our border walls make unreachable.

## Gotchas

- Write via OS shadow registers (`SDMCTL`, `GPRIOR`, `PCOLR0/1`, `COLOR0-4`, `CHBAS`, `SDLSTL/H`), not direct GTIA/ANTIC registers, except `GRACTL/HPOSP0-3/HPOSM0/HPOSM1/PMBASE`.
- PMG layout (single-line, `SDMCTL = $3E`, positions in scanlines): missiles `PMG+$300`, P0 `+$400`, P1 `+$500`, P2/P3 `+$600/+$700` = enemy bullets (the player's bullet writes whole bytes of the missile area, so don't put anything else in M2/M3). The bullet is the 4 rows of `bala_icono`, each drawn on 2 lines. Erase-before-draw: `borrar_jugador`/`borrabala` run before moving/painting; `limpiar_pmg` clears all 2 KB (stage start, messages, title) and resets `activa` and `eb_activa`.
- Sound is a countdown: `sonar` (A = `SND_*`) sets `sndtim = 8`; `actualizar_sonido` must zero `AUDC1` at 0 or the tone drones. `modo_texto` silences it.
- Playfield limits are a safety net behind the walls: player x 50–200, y 40–198; bullet dies outside x 48–206, y 40–216.
- `icl` paths are relative to the project dir; keep all `.asm` files flat in the repo root.
- Long branches: `bala.asm` grew past the ±127 byte range once (`bcc pintabala`); use `bcs skip / jmp` when MADS reports "Branch out of range".

## Editor (`editor-sprite.html`): sprites and levels

- Visual sprite editor (open in any browser, no build step): 128-color Atari palette; the Kaiju poses (8×24, always multicolor) and `KAIJU_PCOLR0/1` (keys 1-4 pick their color); the 11×3 lives icon (not drawn by the game any more); the 2×4 bullet (its color is COLOR3, shared with enemies); background/text brightness. Pencil/eraser/fill, undo, shift/mirror/copy, animation preview.
- "Niveles" panel (`#pniveles`): level editor writing `niveles.asm`. List (new/duplicate/delete/reorder, names go in the label comment), parts grid (`nancho`/`nalto` selects, `redimensionar` keeps parts by grid position; thumbnails in `#npartes` select `nParte`, the part being edited; objects get `parte = nParte`), map canvas 640×384 (16 px per char) with tools bloque/rect/relleno (right button = empty, optional left-right mirror; every tile write goes through `setTile`, which also writes the opposite edge cell of the neighbouring part so gaps always match; `dibujarBordes` shows arrows on gaps and the neighbour's number), jugador, celula, robot (click = place/select, drag = move, right = delete), zona (drag the selected robot's watch zone). Robot form, patrol preview (`recorrido`, same rules as `actualizar_enemigos`), warnings (per part: gaps without a neighbour, gaps smaller than the player — 3 rows / 2 cols —, blocks right behind a gap; per level: parts with cells that can't be reached from `parteIni`) and byte budget (`PRESUPUESTO`, measured free space for levels; update it if code grows a lot). Own undo stack (Ctrl+Z goes to levels when the last click was in that panel) and `localStorage` key `atari-juego-niveles`. Output: download/copy `niveles.asm`; input: open file or paste. The pure format code (`nivelNuevo`, `mapaBorde`, `migrarNivel` for old drafts, `vecino`, `comprimirFila`, `exportarNiveles`, `leerNiveles`, `recorrido`) has no DOM and can be tested with node. `NIVELES_ASM` is a hardcoded copy of `niveles.asm` (also fetched over http): refresh it if `niveles.asm` changes outside the editor.
- Its "Prueba" scene is only a **preview** of movement, animation and shooting on the levels of the Niveles panel (it also changes part through gaps, `salirDemo`) (blocks, breakable blue blocks +1): no enemies, cells, stages or Kaiju HUD. It embeds `kaiju_fuente` (`FUENTE_K_B64`) and `KAIJU_COLOR0-2` (`KAIJU_PF`); refresh them if those change.
- Export emits `.byte` blocks for `datos.asm` (`vida_icono`, `bala_icono`), a `lda/sta` color block for `iniciar` in `main.asm` (only COLOR3/COLOR4 and similar still apply; robot colors live in `KAIJU_PCOLR0/1`), and a `kaiju_graficos.asm` block (equates + `kaiju_<pose>_p0/_p1`). Apply the parts that changed when the user pastes it.
- Import finds byte blocks by label (order-independent) and colors by `lda #…`/`sta REG` pairs. Drafts autosave to `localStorage`. `INICIAL` (and `INICIAL.kaiju`) are hardcoded copies of the data: refresh them every time those bytes change.

## Kaiju resources (`kaiju_*.asm`)

- Converted from the Kaiju disk (`~/KAIJU CODIGO FUENTE/`, cc65-compiled — no C or asm source), verified byte-for-byte.
- `kaiju_graficos.asm`: `KAIJU_*` color equates, 7 poses (`sin_usar` unused), 4 shot frames (unused: we keep our missile bullet), `kaiju_fuente` (57 ANTIC 4 chars, codes $02-$3A, copied over the ROM font at `FUENTE+$10`), texts in screen codes terminated by **$FF** (space is code 0).
- `kaiju_titulo.asm` + `kaiju_titulo.mic` (binary via `ins`): 196 lines of the 160×240 ANTIC E picture, split at $6000/$7000.
